## 步驟三：loop / graph 設計說明

**流程**：取得資料 (A) → 資料檢查 (A') → 先討論：摘要 → 規劃 → 新手批評 → 修訂 (B) → **規劃覆蓋度檢查 (B5，v2 新增)** → 人工確認 → 生成 Wiki 頁 (C) → Wiki 檢查 (D) → 查詢 Wiki (E) → 產生投影片 → 投影片檢查 (F) → 渲染 HTML (G) → 最終檢查 (H)

| 節點 | 做什麼 | 會不會重複執行 |
|---|---|---|
| A / A' | 從維基百科 API 抓 7 篇；少於 800 字或抓失敗就排除，通過 < 5 篇直接停 | 每篇一次 |
| B 先討論 | 逐篇摘要 → 規劃 7 頁 → 「大一新生」角色批評 → 修訂 | 摘要每篇一次；批評→修訂 1 輪 |
| B5 覆蓋度檢查 | 每頁的問題能不能只靠指定來源回答？不行就縮小問題或換來源 | 每頁一次 |
| C → D | 生成一頁 → 規則檢查（引用數、引用合法、連結存在、簡轉繁）→ LLM 對照原文查核 | **loop**：不通過帶錯誤回饋重生，最多 2 次 |
| E → F | 每張投影片先查 Wiki 選 1–3 頁 → 只根據這些頁產生 JSON → 格式檢查 → 根據檢查 | **loop**：不通過重生該張，最多 2 次 |
| llm_json | LLM 回的 JSON 解析失敗就把錯誤丟回去 | **小 loop**：最多 3 次 |
| G / H | Python 模板渲染 HTML；檢查標籤成對、張數、每張都有 Wiki 對應、每個 Wiki 頁都被用到、無簡體字 | 一次 |

**為什麼這樣設計**
- **先討論後生成**：直接叫 LLM 寫 Wiki，會寫成教科書。讓「新手」角色先批評規劃，實際上把「歷史沿革」頁拿掉、把 0050 實例提前到第 2 頁。
- **便宜的檢查先做、貴的後做**：規則檢查不花錢、零誤差，先擋掉格式問題；過了才叫 LLM 做事實查核。
- **LLM 只產內容、不寫 HTML**：版面由 Python 模板控制，HTML 不會壞，最終檢查只要驗結構。
- **每張投影片都記 `wiki_refs`**：Wiki 和簡報的對應關係可以被檢查（H 節點檢查「每個 Wiki 頁至少被用到一次」）。
- **重試有上限**：超過 2 次就保留最後版本並標上 ⚠️，不讓流程無限卡住。

## 步驟四：反思

**哪一個節點最常出錯？**
D（Wiki 檢查）。v1 裡 13 次檢查失敗 8 次，`etf-asset-types` 和 `etf-costs-and-fees` 重生 3 次都沒過。看失敗原因有兩種：
1. **真的幻覺**：規劃要求 `etf-asset-types` 講「債券、商品、加密貨幣 ETF」，但指定的來源 S1、S2 沒有細講，LLM 只好用自己的知識補，就被查核擋下。重生時它換一個說法再補，所以一直失敗。
2. **檢查器誤判**：查核者只拿到「來源摘要」，但生成者拿到的是「摘要＋原文節錄」。原文有、摘要沒寫的事實（例如 0050 不課徵證券所得稅）就被判成無根據。另外簡繁檢查把正體的「吃」當成簡體（OpenCC 會轉成「喫」），S1 的維基網址本身也是簡體，造成最終檢查誤判 FAIL。

**發現問題後，把檢查往前移到了哪一個步驟？**
移到 **B（規劃）之後、C（生成）之前**，新增 **B5 規劃覆蓋度檢查**：每頁生成前先問「這頁的問題只靠指定來源答得出來嗎？」。v2 裡 B5 修正了 2 頁：把 `etf-types-and-distribution` 從「高股息 vs 市值型的選股差異」（來源沒講）縮小成來源能回答的「股票指數型與商品型 ETF 的差異、配息週期發展」。問題在規劃時就解決，D 不必用重生 3 次的方式硬撐。

**有沒有因此修改 workflow / graph？為什麼？**
有，改了三處：
1. graph 加上 **B5 節點**（上面說明），理由是錯誤的根源在規劃，在下游重生只會一直失敗。
2. **D 的事實查核改用和生成者同一份證據**（`source_pack`：摘要＋原文節錄）。檢查者和生成者看到的資料不一樣，檢查本身就不公平。
3. **簡繁檢查排除 OpenCC 的異體字對應（吃/喫、台/臺）並忽略網址**，避免假警報淹沒真正的問題。

結果：v2 的 Wiki 7 頁全部第一輪通過，最終檢查 5/5 PASS。這次學到的是：**loop 不是重試越多越好**，同一個節點一直失敗時，原因常在上游的輸入或檢查器本身，該做的是把檢查往前移或修檢查器，而不是加重試次數。
